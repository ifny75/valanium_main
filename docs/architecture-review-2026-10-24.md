# Обзор архитектуры Valanium — 24 октября 2026

## Область обзора

Статический обзор структуры репозитория и ключевых точек Rust-ядра, Android, Windows и сервера. Это не исчерпывающий аудит безопасности. Код приложения не изменялся. Локальные изменения VPN-клиента сохранены.

## Карта системы

- `valanium-core`: криптография, MLS, локальное SQLite-хранилище, команды/события и сетевой движок.
- `valanium-android`: Java UI → JNI → Rust; Android Keystore и foreground service.
- `valanium-windows`: Tauri → Rust; отдельный процесс Onionize.
- `valanium-server`: Node/TypeScript, uWebSockets, SQLite; регистрация, доставка, публичные каналы, оплата и поддержка.
- `deploy`: эксплуатация и подпись выпуска; `valanium-site`: сайт.
- `valanium-vpn-main`: отдельная VPN-система на FastAPI/WireGuard с собственным Tauri-клиентом.
- `valanium-onionize`: отдельный Rust-проект со своим вложенным `.git`.

Сильная основа: общее ядро для клиентов, узкая граница команд/событий, отдельные модули криптографии и протокола, тестируемый сервер. Сохранять эти границы при рефакторинге.

## Предлагаемые изменения по приоритету

### 1. Явная политика очередей и восстановления UI

Основание: `valanium-core/src/client.rs`, `Engine::start` использует `mpsc::unbounded_channel`; в `valanium-core/src/ffi.rs`, `Queue::push` удаляет старейшее событие при достижении 4096 элементов. `Events.java` затем ставит каждое событие в очередь главного Android-потока через `Handler.post`.

Риск: память входящих команд не ограничена, а UI при отставании может пропустить изменение состояния. Лимит числа событий также не ограничивает их суммарный размер.

Предложение: лимиты по количеству и байтам, явный результат `busy` для submit, объединение повторяющихся статусных событий. Для важных изменений — последовательный номер и событие `resync_required`, после которого UI перечитывает состояние из ядра. Не блокировать UI ожиданием свободного места. Отдельно определить завершение сессии при заполненной очереди.

Проверка: остановить poll, отправить больше лимита команд и событий; проверить верхнюю границу памяти, восстановление состояния UI и завершение без зависания.

### 2. Разделить Android UI и движок по ответственности

Основание: `MainActivity.java` — около 6364 непустых строк; `client.rs` — около 4164. Размеры измерены по текущим файлам, не являются самостоятельным доказательством дефекта.

Предложение для Android: оставить Activity управление жизненным циклом и навигацией; вынести экраны чата, профиля, регистрации и настроек в отдельные классы; ввести единое состояние экрана и преобразование событий в это состояние. Для этого не обязательно добавлять AndroidX.

Предложение для Rust: выделить маршрутизацию/переподключение, обработчики команд по предметным областям и доставку/outbox. Сохранить единственного владельца состояния MLS и БД; не распараллеливать их запись автоматически при разделении файлов.

Проверка: сохранять текущий JSON-контракт; сценарии регистрации, reconnect, отправки, истории и logout должны проходить до и после каждого небольшого переноса.

### 3. Зафиксировать контракт Rust ↔ Java ↔ TypeScript

Основание: команды/события определены в `command.rs`, Java формирует JSON, сервер имеет собственные структуры кадров. Граница узкая, но совместимость требует отдельных проверок.

Предложение: версионированные образцы команд, событий и бинарных кадров, которые читают тесты всех участников; явные правила неизвестных полей/опкодов и совместимости версий. Начать с fixtures и тестов, затем при необходимости генерировать DTO из одного источника. Не менять формат передачи только ради генератора.

Проверка: Windows и Android обрабатывают одинаковые образцы; предыдущая версия клиента проверяется против новой версии сервера.

### 4. Сделать выпуск воспроизводимым

Основание: в `release` много APK; имена файлов не доказывают внутреннюю версию. `deploy/sign-apk.mjs` уже правильно выделяет подпись и ротацию ключа в отдельный шаг. В главном Git-репозитории не найдено отслеживаемых файлов `.github` — наличие CI вне GitHub не проверялось.

Предложение: единая команда сборки/подписи/проверки, манифест с commit, versionCode, SHA-256 APK, ABI и версиями инструментов. CI: Rust tests, TypeScript check/tests, Java/JNI contract, Android assemble и проверка подписи. Ключ выпуска остаётся вне репозитория. Зафиксировать происхождение Onionize через workspace/submodule или документированный отдельный release, чтобы чистый checkout воспроизводил зависимости.

Проверка: сборка из чистого checkout; обновление поверх предыдущего APK с сохранением аккаунта; запуск на Pixel, загрузка JNI, проверка совместимости нативных библиотек с размером страниц устройства.

### 5. Обновить документацию до фактического поведения

Основание: Android README описывает необходимость внешнего Tor и перечисляет отсутствующие возможности, тогда как `cargoNdk` включает `tor-embedded`, `Core.java` содержит запуск Tor, а команды включают Verify. Корневой архитектурный документ говорит о пяти C-функциях, комментарий `lib.rs` — о четырёх; JNI имеет дополнительные методы. Принцип «ключи никогда не покидают устройство» требует уточнения рядом с описанием зашифрованного восстановления на сервере.

Предложение: отдельные разделы «реализовано», «ограничения», «план»; точная граница между открытыми каналами и E2EE-перепиской; различать экспорт открытого ключевого материала и зашифрованную резервную копию. Документировать Android foreground service как ограниченный жизненным циклом платформы: `onTimeout` уже реализован, обещание постоянной связи требует отдельного механизма пробуждения.

### 6. Разделить эксплуатационные области

VPN, мессенджер, сайт и поддержка имеют разные зависимости и циклы выпуска. Сначала описать владельцев, команды сборки, deployment и границы конфигурации для каждого; вынести QA-снимки и APK в каталог артефактов. Разделение Git-репозиториев делать только при реальной необходимости независимых доступов/релизов. Микросервисы вместо текущего relay не требуются по результатам этого обзора.

## Порядок работ

1. Зафиксировать контрактные fixtures и сценарии reconnect/logout.
2. Ввести управление очередями и явную пересинхронизацию.
3. Небольшими шагами выделять экраны и обработчики без изменения протокола.
4. Автоматизировать выпуск, затем привести документацию и структуру артефактов в порядок.
