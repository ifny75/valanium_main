# Сопряжение аккаунта: QR + локальный Wi-Fi

Реализовано в общем Rust-ядре, Android UI/JNI и Windows UI/Tauri этого монорепозитория. Это **подключение дополнительного устройства**, а не клонирование БД. Телефон остаётся активным, ПК создаёт свой ключ устройства и новое состояние MLS. Чаты, сообщения, фото и голосовые вложения переносятся потоковым снимком истории. Старые приватные ключи устройства, снимки MLS и исходящая очередь не копируются. Существующий файловый экспорт остаётся отдельным режимом полного переезда одного устройства.

## Как подключить телефон к ПК

1. Открыть Valanium на ПК без аккаунта и оставить окно активным. На экране входа выбрать «Подключить аккаунт с телефона по QR и Wi-Fi». ПК показывает одноразовый QR.
2. Открыть телефон в той же Wi-Fi сети. По умолчанию при открытом приложении оно ищет готовые устройства и предлагает подключение. Либо открыть настройки → данные → «Подключить устройство по QR и Wi-Fi».
3. На телефоне выбрать «Сканировать QR камерой» и навести камеру на экран ПК. Разрешение камеры требуется только для сканера; фотографии не сохраняются. Альтернатива — вручную передать строку кода сопряжения.
4. Сверить код из четырёх групп символов на обоих экранах. Только если он совпадает, нажать подтверждение **на обоих устройствах**. На исходном устройстве должен быть доступен ключ разблокированной базы; Windows дополнительно запрашивает пароль приложения, если он установлен. Если Android Keystore уже требует повторной аутентификации, сначала разблокировать приложение и повторить сопряжение.
5. ПК устанавливает ту же личность с новым ключом устройства и подключается к обычному серверу через выбранный Tor-маршрут. Телефон продолжает работать. Перенесённые чаты с содержимым появляются на ПК. Для новых сообщений ядро создаёт собственные MLS-каналы с сохранением общей нити истории. История групп переносится как архив: чтобы продолжать писать с нового устройства, его нужно легитимно добавить в группу. Снимок фиксирует историю на момент начала экспорта, а не непрерывно синхронизирует изменения старых сообщений.

Обнаружение устройств отключается переключателем «Находить устройства в локальной сети». Ручное подключение из настроек доступно и при отключённом поиске. Готовность к приёму автоматически объявляет только открытое приложение **без аккаунта**. Уже существующий аккаунт не перезаписывается. Устройство без запущенного Valanium не обнаруживается.

## Протокол и граница доверия

- `pairing_listen`: получатель открывает временный TCP-порт, создаёт случайный ID сессии (128 бит) и PSK (256 бит), выдаёт QR `valanium-pair:v2:`. QR и ожидание сопряжения ограничены тремя минутами; после подтверждения потоковая передача может продолжаться до часа. В QR только версия, ID, локальные IPv4-адреса, порт и секрет сессии; ключей аккаунта и истории там нет.
- Поиск: UDP broadcast на порту **49173** с новым случайным nonce каждого запроса. Ответ содержит тот же nonce, случайный ID сессии и порт. Ответы принимаются только из локальной подсети, число предложений ограничено. Аккаунт, имя пользователя и постоянный ID устройства не объявляются. Это подсказка интерфейса, **не аутентификация**.
- `pairing_connect`: адреса из QR должны быть числовыми частными/link-local IPv4, DNS и публичные адреса запрещены. Канал — библиотечный **Noise_NNpsk0_25519_ChaChaPoly_SHA256** (`snow`). Случайные эфемерные ключи и PSK защищают канал; ID сессии включён в prologue. Проверочный код из четырёх групп по четыре hex-символа (64 бита) выводится из полного хеша рукопожатия.
- `pairing_confirm`: после ручной сверки обе стороны посылают аутентифицированное подтверждение. Исходная сторона дополнительно проверяет локальный ключ открытия БД в ядре. Ключ не возвращается из Tauri в WebView. Только после двух подтверждений передаётся минимальная посылка с ключом личности, отображаемым именем, настройками приватности и адресной книгой (включая блокировки и локальные имена).
- Получатель генерирует **новый** приватный ключ устройства. Проверка пустой базы, запись ключей, имени, приватности и адресной книги выполняются в одной SQLite-транзакции. История читается отдельным соединением SQLite в согласованном read-снимке и передаётся через ограниченный канал, не собираясь целиком в RAM. Получатель шифрует временные записи собственным ключом БД, а затем атомарно устанавливает аккаунт, карту чатов и все сообщения; неполный поток не устанавливается. После завершения зашифрованные временные записи удаляются. Получатель подтверждает завершение после устойчивой записи. Если последний ACK теряется, получатель показывает установленный аккаунт, а источник может показать ошибку связи; перед повтором нужно проверить второй экран. При потере последнего ACK новая копия не становится клоном старого устройства: у неё собственный device key.
- Внутренняя команда установки не десериализуется из публичного JSON API. Установка привязана к активной подтверждённой сессии. Отмена/истечение срока закрывают слушатель и очищают сохранённый QR. Повторное использование завершённого QR не создаёт новую сессию.
- Кадр ограничен 4096 байтами до выделения памяти; операции ввода/вывода ограничены таймерами. Метаданные аккаунта ограничены 2 МиБ, отдельная запись истории — 16 МиБ, временная история — 8 ГиБ сериализованных записей. Каждая запись передаётся аутентифицированными порциями; память ограничена несколькими записями, не размером всей БД. Для атомарной установки нужно дополнительное свободное место под зашифрованный staging и SQLite WAL. Аккаунтные секреты в сетевых буферах используют `Zeroizing`. Идентичность не проходит через JS или Java UI при передаче. QR и код не записываются в настройки, логи и аналитику.

Команды: `pairing_listen`, `pairing_discover {enabled}`, `pairing_connect {qr}`, `pairing_confirm {session,unlock}`, `pairing_cancel`. `unlock` — hex байтов ключа локальной БД исходного устройства, не пароль файла экспорта. Android получает его из Keystore; Windows использует отдельную native-команду `pairing_confirm` и DPAPI. На получателе поле не требуется.

События: `pairing_found {session,address}` и `pairing {session,state,code,qr,qr_svg}`. Состояния: `listening`, `connecting`, `verify`, `transferring`, `complete`, `failed`, `cancelled`. Передача показывает число обработанных записей. UI сбрасывает QR при завершении/отмене. Поиск и слушатель останавливаются при уходе Android в фон, потере фокуса/скрытии окна Windows и закрытии ядра. Обычная переписка продолжает идти через Tor; локальное сопряжение явно использует LAN и раскрывает локальные адреса двум устройствам.

## Ограничения и проверки

Поддерживается локальная IPv4-сеть. IPv6-only, отдельные VLAN, гостевые сети с изоляцией клиентов и блокировка входящих соединений Windows могут мешать соединению. Разрешите Valanium доступ к частной сети в Windows. Если broadcast блокируется, можно начать подключение вручную по QR, если TCP между устройствами разрешён. Автоматического обхода изоляции сети и перехода через внешний relay нет.

Проверки:

```sh
cargo test --manifest-path valanium-core/Cargo.toml pairing::tests --lib
cargo check --manifest-path valanium-android/rust/Cargo.toml --lib
cd valanium-windows
npm test
npm run test:ui
```

Тесты ядра используют два независимых движка/БД и настоящий локальный TCP, включая многомегабайтную историю и изображение. Проверены атомарный откат при неполной истории и отсутствие клонирования MLS. Также проверяются: два подтверждения, неверный ключ локальной БД, неверный PSK, отмена, повторный QR, свежий device key, имя, адресную книгу с блокировками и приватность (включая передачу несколькими кадрами), запрет перезаписи аккаунта, искажённый/повторный шифротекст, привязка сессии, срок жизни и ограничение размера кадра. Браузерная проверка использует имитацию Tauri: показ QR, предложение по обнаружению, ручное подтверждение на получателе и native-подтверждение на источнике.

Android Java/XML и JNI проверяются отдельно. APK, реальная камера Android, Windows-бинарник и два физических устройства в Wi-Fi в этой сессии не проверялись. Перед выпуском нужна проверка телефона и ПК, смены Wi-Fi, пароля/системной блокировки, отмены и правил Windows Firewall.

Протокол истории имеет версию QR v2; обновите оба клиента и создайте новый QR. Публичные каналы загружаются своим серверным механизмом, перенос не обходит членство или права на групповые переписки. Список собственных устройств обновляется в рабочем соединении раз в минуту, чтобы новое устройство и отзыв ключей распространялись без ручного перезапуска.
