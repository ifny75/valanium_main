# Valanium VPN — архитектура

Свободный VPN-сервис: клиент, узлы и плоскость управления. Весь стек — открытый
исходный код без платных зависимостей; вход бесплатный, по коду доступа.

Документ — контракт между слоями, как и `ARCHITECTURE.md` мессенджера. Пишем код
по нему, а не по внутренним договорённостям. Всё, что помечено «сейчас», описывает
состояние на 2026-09-07; всё остальное — целевое состояние с указанием фазы.

---

## 1. Принципы

1. **Сервер не должен знать, кто куда ходил.** Не «обещаем не смотреть», а «нечего
   отдать по запросу»: связки «личность ↔ трафик» в схеме нет.
2. **Ключи не покидают устройство.** Приватный ключ WireGuard рождается на клиенте.
   Сервер видит только публичный.
3. **Личность — ключ, а не логин.** Ed25519 challenge-response. Паролей на сервере нет.
4. **Плоскость управления отделена от плоскости данных.** Кто имеет право — решает
   один сервис; трафик носит другой. Компрометация узла не отдаёт список пользователей.
5. **Fail closed.** Обрыв тоннеля — блокировка трафика, а не тихий выход в открытую сеть.
6. **Не изобретать криптографию и не изобретать транспорт.** WireGuard, Ed25519,
   готовые обфускаторы. Самодельная маскировка — только как заведомо временная.
7. **Проверяемость.** Узел можно поднять свой, клиент собрать самому, релиз сверить
   по подписи.

## 2. Модель угроз

### Защищаем от

| Противник | Механизм |
|---|---|
| Провайдер, видящий трафик пользователя | WireGuard: содержимое и адреса назначения зашифрованы |
| DPI, отличающий VPN от обычного трафика | UDP:443 + маскирующий транспорт (§8) |
| Изъятие диска узла | На узле нет ни личностей, ни истории — только текущий список публичных ключей |
| Изъятие базы плоскости управления | Нет приватных ключей WG, нет IP, нет журнала соединений (§7) |
| Кража клиентского бинарника | В клиенте нет учётных данных сервиса: только его собственный ключ (§5) |
| Утечка при обрыве тоннеля | Killswitch на уровне ОС (§9) |
| Связывание оплаты с трафиком | Слепые жетоны доступа (§6), фаза 4 |

### НЕ защищаем (осознанно)

- **Глобальный наблюдатель.** Один хоп не спасает от корреляции входа и выхода по
  времени и объёму. Кому нужно от этого — Tor, а не VPN; в мессенджере он уже есть.
- **Сам оператор узла.** Узел по определению видит, куда идёт трафик после
  расшифровки. Мы уменьшаем то, что он может **связать с личностью**, а не то,
  что он видит.
- **Скомпрометированное устройство.** Root или кейлоггер ломает всё.
- **Анонимность на прикладном уровне.** Вход в почту через VPN деанонимизирует
  пользователь, а не сеть.
- **Принуждение оператора.** Мы уменьшаем то, что можно изъять, но не сопротивляемся
  изъятию.

## 3. Что есть сейчас

Один боевой узел `valanium-hop1` (2.27.205.9), Debian 13, 1 vCPU / 2 GiB / 40 GiB.
Раньше был relay мессенджера, выведен из этой роли и занят под VPN.

```
клиент (Tauri, Windows)
  ├── /v1 ────────────► TCP:62740 ┐  вход по коду, подпись устройства
  ├── wireguard.dll ──► UDP:443 ──┤  valanium-hop1
  └── TLS-маска ──────► TCP:443 ──┤
                                  ├─ vpn_node   (uvicorn :8000, закрыт ufw)
                                  ├─ main_server (uvicorn :62740, ОТКРЫТ в мир, HTTP)
                                  ├─ unbound на 10.10.0.1 — резолвер тоннеля
                                  └─ wg0 10.10.0.1/24
```

`/v1` развёрнут и проверен живьём: код доступа → привязка устройства → вход
подписью → регистрация публичного ключа WireGuard на узле → отзыв со снятием
пира. Резолвер тоннеля свой, запросы клиентов не уходят третьей стороне.

Работает и остаётся: агент узла (`wg syncconf` без разрыва чужих сессий, метаданные
пиров в `peers.json`, счётчики из `wg show dump`), настоящий тоннель на клиенте
(`wireguard.dll` напрямую, маршруты через `netsh`), релей маскировки, блокировка
Tor и торрентов на выходе, планировщик сроков и трафика.

Не работает как сервис всё, что касается «кто это подключается» — §5 и §12.

## 4. Целевая архитектура

```
┌──────────────────────────────────────────────────────────────┐
│ клиент (Windows · Android · Linux)                           │
│  ключ личности Ed25519 · ключ WireGuard · killswitch         │
└───────────────┬──────────────────────────┬───────────────────┘
                │ HTTPS /v1 (control)      │ WireGuard (data)
                ▼                          ▼
┌───────────────────────────┐   ┌──────────────────────────────┐
│ valanium-vpnd             │   │ узлы: node-agent + wg0       │
│ право доступа, устройства │──▶│ слушает ТОЛЬКО mesh-адрес    │
│ квоты, каталог узлов      │   │ состояние = список pubkey    │
│ SQLite, без IP и истории  │   │ ничего о личностях не знает  │
└───────────────┬───────────┘   └──────────────────────────────┘
                │ unix socket
        ┌───────┴────────┐
        │ админка        │  недоступна из интернета: SSH-туннель
        │ (Jinja2/HTMX)  │  или .onion. Публичного порта нет.
        └────────────────┘
```

**Три решения, которые определяют всё остальное.**

**Плоскость управления отделена от плоскости данных.** Сейчас панель — одновременно
админка, API клиента и хранилище приватных ключей WG. Разделяем: `vpnd` знает,
*кто имеет право*, узел знает, *какие публичные ключи впустить*. Узел не может
перечислить пользователей, потому что у него их нет; `vpnd` не видит трафика.

**У клиента нет учётных данных сервиса.** Ни админского пароля, ни API-ключа —
только собственный ключ, которым он подписывает нонс. Украденный бинарник даёт
ровно ничего.

**Админка не имеет публичного порта.** Не «префикс пути, который трудно угадать»,
а слушающий unix-сокет: не пускает не тот, кто не знает URL, а тот, кто не на машине.
Доступ — `ssh -L` или скрытый сервис Tor (Arti уже есть в `valanium-onionize`).

### Язык плоскости управления

Остаётся Python/FastAPI: код работает, узел однопроцессорный, переписывание 1.5k
строк ради единообразия — не та цена. Но **строгая проверка подписи Ed25519
обязательна** (§5), а значит в `vpnd` едут те же девять тест-векторов, что в ядре
мессенджера. Расхождение реализаций ловится тестом, а не отзывом ключей.

Альтернатива — переписать `vpnd` на Rust и переиспользовать `ed25519-dalek::verify_strict`
из `valanium-core`. Дешевле сделать это, только если плоскость управления всё
равно переписывается по другой причине.

## 5. Идентичность и ключи

Ни телефонов, ни email, ни паролей.

| Секрет | Где рождается | Где живёт | Назначение |
|---|---|---|---|
| Код доступа | сервер, при выпуске | на бумаге у человека; в базе только scrypt-хеш | привязать устройство |
| Device (Ed25519) | клиент | на устройстве | вход и отзыв |
| WireGuard (X25519) | **клиент** | приватная часть только на устройстве | тоннель |
| PSK пира (32 байта) | клиент | клиент + узел | опционально, поверх WG |

**Код доступа — как номер счёта у Mullvad: ни почты, ни имени, ни пароля.**
Отличие одно и существенное: у Mullvad номер счёта — постоянный пароль, он
едет на сервер при каждом входе. Здесь код тратится **один раз**, на привязку
устройства, а дальше устройство входит своей подписью и код по проводу больше
не ходит.

```
Привязка (код на проводе ровно здесь и больше нигде)
1. C → S   POST /v1/hello    → { nonce(32B), serverTime }
2. C → S   POST /v1/devices    { code, devicePub, sig }
3. S       проверяет: nonce наш, не старше 30 с, не использован
                      sig = sign(device, "valanium-vpn-enroll-v1"||nonce||devicePub)
                      scrypt(код, перец) есть в accounts, аккаунт жив
                      число устройств не превышает тариф
4. S → C   { token, expiresIn, account }

Вход (кода нет)
1. C → S   POST /v1/hello    → { nonce }
2. C → S   POST /v1/auth       { devicePub, sig }
             sig = sign(device, "valanium-vpn-auth-v1"||nonce||devicePub)
3. S → C   { token, expiresIn, account }
```

Формат кода — 20 знаков, четыре группы по пять: 16 случайных (80 бит) плюс
четыре знака контрольной суммы. Алфавит base32 без `I`, `L`, `O`, `U`; при
разборе `I`/`L` читаются как `1`, `O` как `0` — человек, который написал букву,
не получит «неверный код». Контрольная сумма нужна не для криптографии, а
чтобы опечатка называлась опечаткой: без неё любой промах выглядит как «такого
счёта нет», и человек идёт в поддержку вместо того, чтобы перечитать четвёртую
группу.

В базе — только `scrypt(код, перец)`, детерминированно, иначе искать по
предъявленному коду пришлось бы перебором всей таблицы. Перец лежит файлом
рядом с базой: без него украденная таблица бесполезна, а 80 бит энтропии
делают перебор безнадёжным и при известном перце.

**Подсмотренный код позволяет привязать чужое устройство** — это цена того,
что кроме кода у человека ничего нет. Ограничивает ущерб лимит устройств и то,
что список устройств виден в клиенте: чужое там заметно и отзывается одной
подписью.

Доменные префиксы обязательны и **отличаются от мессенджерских**: подпись,
дающая доступ к переписке, не должна открывать VPN, и наоборот.

**Проверка строго по RFC 8032.** Режим ZIP-215 принимает точки малого порядка:
ключ из нулей с подписью из нулей проходит проверку — такую «личность» подписал
бы кто угодно. В Rust это `verify_strict`, в Python — libsodium плюс явная
проверка канонической формы `S < L` и отсев малого порядка. Тест-векторы общие
с ядром мессенджера.

**Приватный ключ WireGuard больше не рождается на сервере.** Клиент генерирует
пару, отправляет публичную часть, получает `allowed_ip`, публичный ключ узла и
endpoint. Поле `wg_private_key` уходит из схемы миграцией, существующие подписки
перевыпускаются (фаза 1). Это не косметика: сегодня база на 2.27.205.9 содержит
приватные ключи всех пиров, то есть изъятие диска — это изъятие возможности
расшифровать записанный трафик.

## 6. Право доступа

**Код доступа** (§5) — единственный вход. Открытой регистрации нет: аккаунт
появляется только тогда, когда владелец выпустил код. Бесплатно.

Аккаунт — это строка из хеша кода, тарифа и срока. Ни имени, ни почты, ни
пароля в нём нет; поле `note` для пометки владельца пустое по умолчанию,
потому что любое поле, куда можно записать имя, рано или поздно им заполнят,
а потом изымут вместе с базой.

**Устройства.** Лимит по тарифу проверяется **на сервере**, а не в интерфейсе.
Каждое устройство — строка `(identity, device_pub, добавлено)`, без имени, без
User-Agent, без IP. Отзыв устройства удаляет его пир со всех узлов. Имя вида
«прилагательное-существительное» рисует клиент из отпечатка ключа локально —
серверу оно не нужно и не отправляется.

**Квоты.** Срок и объём остаются, но с поправкой §7: счётчик хранится агрегатом
на подписку, временного ряда `TrafficLog` больше нет.

**Слепые жетоны — фаза 4.** Пока личность привязана к подписке, `vpnd` знает,
какой ключ имеет право войти, и этого достаточно для связывания «человек ↔ узел ↔
время». Цепочка рвётся так же, как это уже сделано для IP в mesh мессенджера
(`deploy/mesh/valanium-blind.js` — там HMAC-псевдоним, здесь нужна настоящая
слепая подпись):

```
1. код доступа или оплата → сервер вслепую подписывает жетон, содержимого не видя
2. клиент разворачивает подпись; у сервера нет способа связать её с выдачей
3. при подключении предъявляется жетон, а не личность
```

Реализация — RSA blind signatures (RFC 9474) либо Privacy Pass (RFC 9578); обе
спецификации открыты, обе имеют свободные реализации на Rust. Цена честная:
отозвать конкретную выданную подписку станет нельзя — только сменить ключ эпохи
и перевыпустить все. Поэтому это отдельная фаза, а не «заодно».

**Оплата — вне scope v1.** Если появится, то механизм TON из мессенджера (§10a
его архитектуры: написан, покрыт тестами, выключен флагом) плюс слепой жетон,
чтобы платёж в публичном реестре не связывался с трафиком.

## 7. Что сервис знает и чего не знает

Это раздел про схему БД, а не про политику. Обещание, не подкреплённое отсутствием
таблицы, ничего не стоит.

**Не хранится нигде:** IP-адрес клиента, журнал подключений и отключений,
DNS-запросы, адреса назначения, история трафика по времени.

**Хранится:** публичный ключ личности, публичные ключи устройств, публичный ключ
WG и выданный `allowed_ip`, срок подписки, суммарный объём трафика (одно число,
без разбивки по времени), узел подписки.

**Живёт в памяти и не пишется:** последний endpoint пира (его держит сам `wg`,
деться от этого некуда), нонсы, счётчики ограничителей.

Что для этого нужно сделать:

- убрать таблицу `TrafficLog` целиком — она существует, чтобы рисовать график,
  а даёт временной ряд активности каждого пользователя;
- `peers.json` на узле лишается `created_at` и `label` с номером подписки: узел
  не должен уметь сопоставить пир с человеком даже косвенно;
- `journald` — `Storage=volatile`, минимальный `MaxRetentionSec`; ufw-логирование
  выключить (сейчас `Logging: on (low)` пишет отвергнутые пакеты с адресами);
- nginx перед `vpnd` — `access_log off`, `error_log` без адресов;
- fail2ban оставить только на SSH; на 443 его не заводить.

**Прозрачность.** `vpnd` отдаёт `/v1/transparency`: версия сборки, хеш схемы БД,
время последнего изменения политики. Это не доказательство — доказательство в том,
что узел поднимается свой (`deploy/`), а клиент собирается из исходников.

## 8. Транспорт и обход блокировок

Три пути, клиент выбирает или пробует по порядку (`Auto`).

| Путь | Что видно наблюдателю | Стоимость |
|---|---|---|
| **Прямой** WireGuard UDP:443 | характерный хендшейк WG, если DPI его знает | нулевая, максимальная скорость |
| **Маска** (текущая, TCP:443 + TLS) | обычная HTTPS-сессия — для **пассивного** DPI | TCP поверх UDP, потери бьют вдвойне |
| **REALITY** (цель) | неотличимо от обращения к настоящему чужому сайту | ~5–10% CPU на узел |

**Текущая маска решает не ту половину задачи.** Она честно описана в `tls_mask.rs`:
самоподписанный сертификат, постоянный SNI `www.microsoft.com`, клиент сертификат
не проверяет. Пассивный DPI действительно видит рядовой HTTPS. Но **активный
проб** — подключиться к 2.27.205.9:443 с тем же SNI и посмотреть, что ответят —
отличает нас от настоящего `www.microsoft.com` за один запрос: там валидная
цепочка, здесь самоподпись. Ровно так и работают системы, которые блокируют VPN
всерьёз.

**Целевой транспорт — VLESS + Vision + REALITY (Xray-core, MPL-2.0).** REALITY не
подделывает сертификат, а перекладывает рукопожатие на настоящий сайт: чужой проб
получает подлинный ответ подлинного сервера, потому что это и есть подлинный
ответ. Своего домена и своего сертификата не нужно — для узла без доменного имени
это ещё и упрощение.

**AmneziaWG (GPLv2)** — средний вариант: правит только хендшейк WireGuard, чтобы
он не опознавался по сигнатуре. Дешевле REALITY и не даёт вида HTTPS. Держим как
второй профиль для сетей, где режут по сигнатуре, но не пробят активно.

Самодельный релей остаётся до фазы 5 и затем удаляется: держать две маскировки,
одна из которых заведомо слабее, — значит гарантированно ловить пользователей
на слабой.

**DNS.** Резолверы внутри тоннеля, DoH по умолчанию, системный DNS не используется.
Текущий выбор AdGuard как «по умолчанию» пересмотреть: это третья сторона, видящая
все запросы. По умолчанию — резолвер на узле; AdGuard остаётся явной опцией.

## 9. Клиенты

**Windows** — есть, Tauri + `wireguard.dll`. Что добавить:

- **Killswitch.** Сейчас при падении тоннеля трафик уходит в открытую сеть. Нужен
  фильтр WFP, блокирующий всё мимо интерфейса тоннеля, — как это делает сам
  `wireguard-windows`. Без него «анонимный VPN» врёт при каждом обрыве.
- **Утечка IPv6.** `wg_nt.rs` разбирает только IPv4 в `AllowedIPs`. На хосте с
  IPv6 весь IPv6-трафик идёт мимо тоннеля. Либо `::/0` в тоннель, либо явное
  отключение IPv6 на время сессии.
- Выкинуть `vpn.rs` (мёртвая заглушка) и остатки плана про NaiveProxy.

**Android** — фаза 6. Переиспользуем структуру клиента мессенджера; тоннель —
официальная библиотека `wireguard-android` (GPLv2), `VpnService` + always-on.

**Linux/macOS** — фаза 6, CLI поверх `wg-quick`: та же `/v1`-аутентификация,
на выходе обычный `.conf`.

Единый ключ личности между мессенджером и VPN — **возможность, а не требование**.
Репозитории раздельные, протоколы совместимые (§5), домены подписей разные. Если
владелец решит объединить вход, `vpnd` научится принимать жетон, выданный
`valanium-server`, — но не наоборот: VPN не должен становиться входом в переписку.

---

## 10. Узлы

Один узел — точка отказа и единственная точка наблюдения. Целевое: три и больше,
клиент выбирает.

- `vpnd` **переезжает с узла трафика на отдельную машину.** Пока они на одном
  хосте, изъятие узла — это изъятие базы пользователей.
- Агент узла слушает **только** mesh-адрес, не `0.0.0.0` (сейчас на :8000 висит
  на всех интерфейсах и спасён одним правилом ufw).
- Ключ агента — не общий на парк, а свой на узел, с ротацией.
- Здоровье и загрузка отдаются в `vpnd` самим узлом (`load`, `peers`, `rtt`),
  клиент показывает настоящие числа вместо нарисованных.
- `setup_node.sh` доводится до полного развёртывания: WG, агент, sysctl, ufw,
  маскирующий транспорт, отключение журналов. Один прогон — рабочий узел.
- Стойки разных операторов и юрисдикций; общего управляющего доступа между узлами
  нет.

## 12. Что сломано прямо сейчас

По убыванию срочности. Первые три — до любой архитектуры.

1. **Клиент ходит в админку под администратором.** В бинарнике зашиты адрес
   панели, логин и пароль (`main_server_client.rs:12`), запрос идёт **по HTTP без
   TLS**. Кто скачал `.exe` — получает полный доступ ко всему парку: список
   пользователей, приватные ключи WG всех подписок, добавление и удаление узлов.
   Пароль виден и любому, кто слушает канал. Считать скомпрометированным, сменить.
2. **Админка открыта в интернет.** `62740/tcp ALLOW IN Anywhere`, plain HTTP.
   Префикс пути — не защита, а отсрочка. Закрыть в ufw до разделения плоскостей,
   доступ через `ssh -L`.
3. **Приватные ключи WG лежат в базе** (§5). Изъятие диска = расшифровка
   записанного трафика.
4. **Пользовательской аутентификации нет вообще.** У `User` нет ни ключа, ни
   пароля; весь `/api/*` — админский. Хранилище логинов в клиенте — `HashMap`
   в памяти с паролями открытым текстом, статус аккаунта выводится из юзернейма
   («blocked», «nosub», «limit» в имени).
5. **Killswitch и IPv6** (§9).
6. **Лимит устройств не проверяется** — список устройств в клиенте один глобальный
   и мок.
7. **Маскировка не держит активный проб** (§8).
8. **Мусор на боевом узле:** правила ufw от роли relay (`51820/udp` от main/hop2/hop4,
   `8081/tcp` на 10.77.0.2, `51821/udp` в мир), старые ключи и конфиги в
   `/etc/wireguard` (`private.key.old-*`, `wg1.conf.old-*`). Открытые двери
   в несуществующие комнаты.
9. **Ни одного теста** во всём проекте.
10. **Нет systemd-юнита и инструкции развёртывания** для плоскости управления —
    есть только `setup_node.sh` для узла.

## 13. Фазы

0. **Останов кровотечения.** Сменить пароль админки, закрыть 62740 в ufw, убрать
   учётные данные из клиента, вычистить старые правила и ключи узла. Дни.
1. **Ключи клиента.** ✅ WG-пара рождается на клиенте, на каждый узел своя;
   наружу уходит только публичная половина. Осталось удалить колонку
   `wg_private_key` вместе со старым админским путём выдачи конфигов.
2. **`/v1` и вход по коду доступа.** ✅ Привязка устройства кодом, вход по
   подписи, устройства и квоты на сервере, отзыв со снятием пира, строгая
   проверка Ed25519 с общими тест-векторами. Клиент перестал быть админом:
   учётных данных сервиса в бинарнике больше нет.
3. **Разделение плоскостей.** `vpnd` отдельно от узла, админка на unix-сокете,
   агент только на mesh-адресе, свой ключ на узел.
4. **Приватность по схеме.** Удаление `TrafficLog` и метаданных пиров, журналы,
   `/v1/transparency`, слепые жетоны.
5. **Транспорт.** REALITY как основной маскирующий путь, AmneziaWG вторым
   профилем, самодельный релей удаляется. Killswitch и IPv6 на клиенте.
6. **Расширение.** Второй и третий узел, Android, Linux-CLI, настоящие
   load/ping, воспроизводимые сборки и подпись релизов.

Фазы 0–2 делают сервис безопасным, 3–4 — честным, 5–6 — пригодным к раздаче.

## 14. Чего не будет

- **Логов «на всякий случай».** Ни для отладки, ни для антифрода.
- **Своей криптографии в тоннеле.** WireGuard как есть.
- **Веб-кабинета пользователя.** Ещё одна поверхность, ещё один пароль, ещё один
  способ связать личность с сессией. Всё в клиенте.
- **Реферальных программ, аналитики, телеметрии.** Ни в каком виде, ни «анонимной».
- **Обещаний скрыть от глобального наблюдателя.** Для этого Tor, и он рядом.
